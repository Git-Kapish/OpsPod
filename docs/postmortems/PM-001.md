# PM-001: Primary provider 429 storm caused a fallback cascade and an invisible backlog

**Status:** resolved and verified. **Severity (as drilled):** SEV-2, customer-visible delay, no
financial impact. **Type:** injected incident (failure injection on a running stack), diagnosed
only from this system's own metrics, alerts and traces. Times are UTC from the host clock.

## Summary

With the primary LLM provider returning 429s, the gateway's fallback absorbed all LLM traffic. The
fallback was sized at half the primary and could not keep up. Callers piled up in the rate
limiter, all 8 worker slots filled with waiting cases, and **every** case, including ones that
need no LLM, queued behind them. Throughput fell from about 52 to 39 cases/min and the oldest
queued case waited 131 seconds. The only latency metric reported 19 seconds, under the 30-second
SLO, so the latency alert stayed silent. One page fired (`LLMErrorRateHigh`) four minutes after the
fault started.

No money moved incorrectly, no case was lost, and no pipeline step errored. The fail-safe design
held; the operability design had gaps. All gaps are now fixed and re-verified with the same drill.

## Impact

- Decision latency for all cases rose from under 1 s to minutes during the fault (queue wait),
  not only for LLM-path cases.
- Throughput dropped about 25% (52.4 -> 38.8 cases/min).
- 0 unauthorized actions, 0 pipeline errors, 0 dead letters, 0 lost cases. Checked in Postgres
  after both drills: all 1,059 cases reached a terminal status (781 awaiting approval, 143
  escalated, 135 resolved), 0 dead letters, 0 failed steps, 0 duplicate idempotency keys, and
  0 payouts on escalated cases.

## Setup (how it was injected)

Stack: API + worker (8 concurrent jobs) + Postgres + Redis + Prometheus/Alertmanager + Jaeger.
`LLM_MODE=fake` with a two-provider config (`config/llm.demo.yaml`): `primary` 60 req/min,
`secondary` 30 req/min. Load: `scripts/load.py --rate 1 --ambiguous 0.8` (about 50 cases/min, 80%
LLM-path, unique complaint text so the gateway cache could not hide provider load). Fault:
`POST /v1/admin/chaos {"llm_429": true, "llm_provider": "primary"}`.

## Diagnosis (from our own telemetry)

1. **Metrics, incident window 10:41:00-10:45:30 vs baseline.**

   | Series | Baseline | Incident |
   |---|---|---|
   | cases/min | 52.4 | 38.8 |
   | p95 processing latency | 0.28 s | 19.3 s |
   | LLM calls ok per min | up to 52 | **pinned at 29.8** |
   | fallback results per min | 0 | 29.8 |
   | breaker_open attempts per min | 0 | 28 |
   | 429 per min | 0 | 1.8 |

   LLM throughput pinned at 30/min is exactly the secondary's configured 30 req/min limit: the
   fallback was saturated, and demand (about 45/min) exceeded it.
2. **Traces (Jaeger).** The slowest `case.process` traces all show the same shape: `llm.call` to
   `primary` for 0 ms with `error=LLMUnavailable` (breaker open), then `llm.call` to `secondary`
   with `fallback_index=1` taking **about 15.9 s**, with `retry_count=0`. The provider was not
   slow; the time was spent waiting for a rate-limit slot inside the span.
3. **Code.** `TokenBucket.acquire` held an asyncio lock while sleeping, so callers queued
   behind each other, and `max_wait` (30 s) only bounded a caller's own wait, not the queue ahead
   of it. With 8 workers each waiting about 2 s per slot, the effective wait was about 16 s.
4. **Why everything slowed.** All 8 worker slots were parked in that queue, so cases that need no
   LLM waited for a free worker: throughput fell and jobs accumulated in Redis.
5. **Why we did not see it.** `opspod_case_duration_seconds` started at worker pickup, so queue
   wait was invisible (19 s reported vs 131 s real). `LLMRateLimitStorm` keyed on raw 429s, which
   the breaker had already hidden. Nothing exported queue depth or age.

## Root causes

1. **Limiter design flaw:** waits were unbounded in practice (lock held while sleeping).
2. **No load shedding:** overload turned into queueing and worker starvation instead of a fast
   hand-off to humans.
3. **Capacity cascade:** a 60 req/min primary failing over to a 30 req/min fallback halves
   capacity at exactly the moment demand moves.
4. **Observability gaps:** the SLO metric excluded queue wait; the storm alert was blinded by the
   breaker; no queue depth/age signal.

## What went well

- The breaker opened within seconds and stopped hammering the failing provider.
- Failure stayed safe: zero unauthorized actions, zero lost cases, zero pipeline errors.
- Case id = trace id made it immediate to go from a slow case to its trace.
- `LLMErrorRateHigh` fired and the webhook delivered it.

## What went poorly

- The headline SLO metric was wrong in a way that hid the user-visible problem.
- Two alerts that should have caught this did not (thresholds and signals designed without a drill).
- During diagnosis I first read Jaeger span durations as milliseconds (they are microseconds) and
  briefly concluded the fallback was fast. The metrics (calls pinned at the rate limit) contradicted
  it, which is what sent me back to the spans.

## Fixes (all shipped and tested)

| # | Change | Where | Test |
|---|---|---|---|
| 1 | Limiter reserves slots and sleeps outside any lock; a wait longer than `queue_wait_s` (default 5 s) is **shed** immediately so the call falls back or escalates | `opspod/llm/resilience.py`, `llm/config.py` | `test_limiter_wait_is_bounded_and_overload_is_shed` |
| 2 | Shedding is not a provider failure: it does not trip the breaker | `llm/gateway.py` | `test_overloaded_primary_sheds_to_fallback_without_tripping_breaker` |
| 3 | Saturated providers fail fast so the case escalates, instead of a 30 s queue | `llm/gateway.py` | `test_all_providers_saturated_raises_unavailable_quickly` |
| 4 | New SLO metric `opspod_case_e2e_seconds` (intake to decision, **including** queue wait); `CaseLatencySLOBurn` now uses it | `pipeline/steps.py`, `infra/alerts.yml` | `test_e2e_latency_and_queue_metrics_exist` |
| 5 | Queue depth and oldest-job age exported; new page `QueueBacklogAge` | `api/main.py`, `api/app.py` | promtool test + metrics test |
| 6 | `LLMRateLimitStorm` also counts `breaker_open`; new `LLMLoadShedding` ticket; limiter wait histogram | `infra/alerts.yml`, `observability/metrics.py` | promtool tests (`make alerts-test`) |
| 7 | Dashboard panels (e2e vs processing latency, queue, limiter wait); runbook sections | `scripts/make_dashboard.py`, `docs/runbook.md` | n/a |

## Verification: same drill, fixed build

Fault injected 10:51:22, cleared 10:57:24, same load. (The "before" column is the incident
window above.)

| Measure | Before | After |
|---|---|---|
| p95 processing latency | 19.3 s | **5.1 s** |
| p95 end-to-end latency (SLO metric) | not measurable | **8.3 s** (SLO 30 s) |
| Throughput | 38.8 cases/min | **57 cases/min** |
| Max queue depth / oldest job age | 81 jobs / 131 s | **4 jobs / 5.4 s** |
| p95 rate-limit queue wait (secondary) | about 16 s | **4.85 s** (bounded by the 5 s limit) |
| Excess LLM demand | queued | **shed: 15 calls/min** |
| Cases escalated to humans (share) | 7.5% | **29.7%** (the price of shedding) |
| Pipeline errors / unauthorized actions | 0 / 0 | 0 / 0 |
| Alerts delivered | `LLMErrorRateHigh` (4m04s) | `LLMErrorRateHigh`, `LLMRateLimitStorm` (3m35s), `LLMLoadShedding` |

The trade is explicit: under a sustained provider outage the system keeps latency and throughput
bounded by sending the overflow (about 30% of cases, up from 7.5%) to the human queue instead of
queueing. For a payments workflow that is the right failure direction.

## Follow-up actions (not done)

- Give LLM-path cases their own queue and worker pool so a provider problem cannot occupy workers
  that deterministic cases need (the shedding bound limits the damage to about 5 s per case).
- Capacity-plan the fallback: it should not be smaller than the primary it backs up.
- Derive limiter rates from observed `Retry-After`/429 behavior instead of static config.
- Re-run this drill against real providers once keys are available; the limits used here are fake.
- `LLMFallbackRateHigh` was already pending before the second drill's fault, an artifact of the
  worker restart resetting counters inside its 10-minute window; consider `increase()` guards.
- `ApprovalQueueBacklog` fires under any sustained load test (the generator sends mostly ambiguous
  cases that need review); tune it against real approver capacity.

## Limitations of this exercise

The providers were fakes with chaos injection, on one machine, with 8 worker slots. Absolute
numbers are specific to this drill; the mechanisms (lock-held sleeps, queue-blind SLI,
breaker-hidden alert signal) are not.
